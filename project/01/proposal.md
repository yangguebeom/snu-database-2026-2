# 2026-2 데이터베이스 학기 프로젝트 1차 기획안

## 1. 프로젝트명

**스터디 모임 통합 관리 플랫폼 (Study Group Management Platform)**

## 2. 프로젝트 주제 및 비즈니스 모델

본 프로젝트의 목표는 대학생과 일반 학습자가 스터디 개설, 참가자 모집, 참여 승인, 일정, 출석, 공지사항 및 학습 활동을 한곳에서 관리할 수 있는 **웹 기반 스터디 운영 서비스**를 개발하는 것이다.

스터디 개설자에게는 구성원·일정·출석 관리 도구를, 참가자에게는 관심 스터디 검색과 참여 신청 및 활동 확인 기능을 제공한다. 초기 서비스는 **무료로 제공하는 스터디 운영 지원 모델**을 채택하며, 결제와 광고 등 수익화 기능은 학기 프로젝트의 구현 범위에서 제외한다.

본 서비스는 단순 게시판을 넘어 회원, 스터디, 참여 신청, 구성원, 모임, 출석 및 활동 데이터를 통합 관리한다. 신청 이력과 실제 구성원 정보를 분리하고, 회원·스터디 간 N:M 관계 및 모임·출석 간 1:N 관계를 관리해야 하므로 관계형 데이터베이스를 활용한다.

## 3. 해결하고자 하는 문제

일반적인 스터디 운영에서 모집, 가입 승인, 일정 안내, 출석과 활동 기록이 여러 채널로 흩어지면 운영자가 현황을 파악하기 어렵다. 참가자 역시 신청 상태와 일정, 공지를 일관되게 확인하기 어렵다.

구체적으로 다음 문제를 해결하고자 한다.

1. **참여 신청 관리의 비효율:** 신청 대기·승인·거절·취소 상태를 한곳에서 확인하고 과거 기록을 보존한다.
2. **구성원·정원 관리의 어려움:** 승인된 구성원과 최대 모집 인원을 연계해 정원 초과를 방지한다.
3. **모임 운영 정보의 분산:** 일정, 출석, 공지 및 학습 활동을 스터디 단위로 연결하여 관리한다.
4. **활동 현황 파악의 어려움:** 구성원 수, 출석률, 게시글 건수 등을 SQL 집계로 제공한다.

## 4. 주요 사용자

| 사용자 유형 | 주요 역할 및 이용 목적 |
| --- | --- |
| 일반 회원(참여 희망자) | 스터디 검색, 상세 정보 확인, 참여 신청, 신청 상태 확인 |
| 스터디 구성원 | 가입한 스터디의 일정·공지 조회, 활동 기록·댓글 작성, 본인 출석 현황 확인 |
| 스터디장 | 스터디 개설·수정, 신청 승인·거절, 정원·구성원 관리, 일정·출석 관리, 공지 게시, 운영 권한 양도 |

회원은 스터디별로 서로 다른 역할을 맡을 수 있으나 **각 스터디의 스터디장은 한 명으로 제한**한다. 스터디장은 해당 스터디의 구성원에도 포함되며, `study_groups.owner_id`와 `study_members.role`이 서로 일치하도록 관리할 계획이다.

| 1. 회원 및 프로필 관리 | 회원 정보 등록, 조회, 수정 |

| 3. 스터디 검색 및 분류 | 제목·키워드, 카테고리, 태그 및 모집 상태를 이용한 검색·필터 |
| 4. 참여 신청 및 승인 | 신청 등록·취소, 대기 목록 조회, 스터디장 승인·거절, 처리 이력 보존 |
| 5. 구성원 관리 | 승인된 구성원 목록 조회, 탈퇴 처리, 스터디장 권한 양도 |

| 7. 모임별 출석 관리 | 스터디장의 출석 상태 입력·수정, 구성원별 출석 내역 조회 |
| 8. 공지사항 관리 | 스터디장의 공지 등록·수정·삭제, 구성원 열람 |
| 9. 활동 기록 및 댓글 | 스터디 구성원의 학습 활동 게시글·댓글 등록·조회·수정·삭제 |
| 10. 활동 통계 | 스터디별 구성원 수, 출석률, 활동 게시글 건수 등 집계 |
| 11. 스터디 태그 | 복수 태그 등록·연결 및 태그 기반 검색 |

### 5-1. 서비스 운영 정책

- 참여는 **스터디장의 승인**을 받아야 완료된다.
- 신청이 취소·거절되어도 신청 기록을 삭제하지 않는다. **재신청은 허용**하며, 과거 신청과 새로운 신청을 별도 건으로 보관한다.
- 스터디에는 **스터디장 1명**만 존재하며, 탈퇴 전 다른 구성원에게 권한을 양도한다.
- 스터디마다 **최대 모집 인원**을 설정하며, 이 인원에는 스터디장도 포함한다.
- 모임 출석은 스터디장이 입력·관리한다.
- 공지사항과 활동 기록의 본문은 해당 스터디 구성원만 열람한다.

### 5-2. 대표 사용자 시나리오

예를 들어 회원이 Python 학습 스터디를 검색하여 참여를 신청하면, 스터디장은 모집 정원을 확인한 후 신청을 승인하거나 거절한다. 승인된 회원은 구성원으로 등록되어 모임 일정과 공지를 확인하고, 스터디장이 기록한 본인의 출석 현황을 조회하며 학습 활동 게시글과 댓글을 작성할 수 있다.

### 5-3. 대표 업무 흐름

**가입 신청 및 승인**

1. 회원이 스터디를 검색하고 참가를 신청한다.
2. 시스템이 신청을 대기 상태로 등록한다(상태 코드 예시: `PENDING`).
3. 스터디장이 대기 신청을 확인하고 승인 또는 거절한다.
4. 승인 시 **스터디장을 포함한 현재 구성원 수**, 정원 및 중복 가입 여부를 검사하고, 신청 상태 변경과 구성원 등록을 **하나의 트랜잭션**으로 수행한다.
5. 거절·취소된 신청도 이력으로 남으며, 재신청 시 새 신청 기록을 생성한다. 동일 회원의 동일 스터디에 대한 **중복 대기 신청을 방지하는 제약조건**을 후속 단계에서 검토한다.

**모임 및 활동 관리**

1. 스터디장이 모임 일정을 등록한다.
2. 구성원은 해당 스터디의 일정·공지를 열람한다.
3. 모임 후 스터디장이 구성원별 출석을 입력한다.
4. 구성원은 학습 활동 게시글과 댓글을 작성한다.
5. 시스템이 구성원 수·출석률·활동 건수를 SQL로 계산한다.

## 6. 예상 테이블 구성 및 데이터 구조

최종 시스템은 **의미 있는 테이블 10개 이상**으로 구성할 계획이며, 현재는 핵심 기능에 대응하는 **12개 테이블을 후보로 선정**하였다. 컬럼명·자료형·PK/FK 및 제약조건의 세부사항은 2~3차 설계에서 검증·조정할 예정이다.

| 번호 | 테이블 | 한 행의 의미 | 주요 컬럼 후보 | 관계 및 존재 이유 |
| --- | --- | --- | --- | --- |
| 1 | `members` | 회원 한 명 | `id`, `name`, `email`, `created_at` | 회원을 독립적으로 식별하고 작성자·신청자를 연결 |
| 2 | `study_categories` | 스터디 분류 한 개 | `id`, `name` | 카테고리를 별도로 관리해 중복 표기를 방지 |
| 3 | `study_groups` | 개설된 스터디 한 개 | `id`, `owner_id`, `category_id`, `title`, `description`, `capacity`, `status` | 스터디장(`members`), 카테고리를 참조하고 정원·모집 상태 관리 |
| 4 | `study_applications` | 참여 신청 한 건 | `id`, `study_id`, `member_id`, `status`, `applied_at`, `decided_at`, `note` | 신청 시점·처리 상태·과거 이력을 보존 |
| 5 | `study_members` | 회원의 스터디 소속 한 건 | `id`, `study_id`, `member_id`, `role`, `joined_at`, `left_at` | 실제 구성원을 신청 이력과 분리하고 권한·탈퇴 관리; 스터디장도 구성원에 포함 |
| 6 | `study_meetings` | 예정 또는 진행된 모임 한 건 | `id`, `study_id`, `title`, `start_at`, `location`, `status` | 한 스터디가 여러 모임을 운영 |
| 7 | `meeting_attendance` | 한 구성원의 한 모임 출석 기록 | `id`, `meeting_id`, `study_member_id`, `status`, `recorded_at` | 참석 여부를 모임 및 구성원별로 기록 |
| 8 | `study_notices` | 공지사항 한 건 | `id`, `study_id`, `author_id`, `title`, `content`, `created_at` | 스터디별 공식 공지와 작성자 관리 |
| 9 | `study_posts` | 학습 활동 게시글 한 건 | `id`, `study_id`, `author_id`, `title`, `content`, `created_at` | 공지와 구분되는 구성원 활동 기록 |
| 10 | `study_comments` | 게시글 댓글 한 건 | `id`, `post_id`, `author_id`, `content`, `created_at` | 게시글에 대한 구성원 의견을 별도 저장 |
| 11 | `study_tags` | 재사용 가능한 태그 한 개 | `id`, `name` | 키워드 표기를 통일하고 공유 |
| 12 | `study_group_tags` | 스터디와 태그의 연결 한 건 | `study_id`, `tag_id` | 스터디와 태그의 N:M 관계 구현; 복합 PK 후보 |

### 6-1. 주요 관계

- `members` **1:N** `study_groups`: 한 회원은 여러 스터디를 개설할 수 있으며 스터디는 한 명의 스터디장을 참조한다.
- `study_categories` **1:N** `study_groups`: 한 카테고리에 여러 스터디가 속한다.
- `members` **N:M** `study_groups`: `study_members`가 실제 소속 관계를 연결한다.
- `members` 및 `study_groups` **각각 1:N** `study_applications`: 회원·스터디별로 여러 시점의 신청 이력을 보존한다.
- `study_groups` **1:N** `study_meetings`: 하나의 스터디에서 여러 모임을 개설한다.
- `study_meetings`와 `study_members` **각각 1:N** `meeting_attendance`: 한 모임의 구성원별 출석 기록을 저장한다.
- `study_groups` **1:N** `study_notices`, `study_posts`: 스터디 단위로 공지·활동 기록을 관리한다.
- `study_posts` **1:N** `study_comments`: 게시글 하나에 여러 댓글이 등록된다.
- `study_groups` **N:M** `study_tags`: `study_group_tags`를 연결 테이블로 활용한다.

### 6-2. 데이터 무결성 및 SQL 활용 계획

- **PK/FK:** 각 테이블의 행을 PK로 고유하게 식별하고, 신청·소속·일정·출석·게시글의 관련 행을 FK로 연결한다.
- **중복 방지:** 동일 회원의 동일 스터디 중복 활성 소속, 동일 모임의 동일 구성원 출석 중복, 같은 스터디·태그 조합 중복을 방지한다.
- **신청 이력:** 기존 신청 기록을 보존하면서 동일 회원의 동일 스터디에 대한 중복 대기 신청을 제한한다. 구체적인 UNIQUE 제약조건 및 인덱스 설계는 3차에서 검토한다.
- **정원 검사 및 트랜잭션:** 승인 시 현재 구성원 수(스터디장 포함)를 확인하고 정원 초과를 방지한다. 동시 승인 상황에서도 데이터 일관성을 보장할 수 있도록 트랜잭션과 잠금 방식을 설계한다.
- **스터디장과 구성원의 일관성:** 스터디 개설 시 스터디장을 `study_members`에도 등록해 모집 정원에 포함한다. 스터디장 탈퇴 시에는 기존 구성원에게 권한을 양도한 후 탈퇴하도록 하며, 소유자 정보 변경과 구성원 역할 변경을 하나의 트랜잭션으로 처리할 계획이다.
- **출석 정합성:** `meeting_attendance`에 연결되는 모임과 구성원은 **같은 스터디에 속해야 하며**, 해당 구성원이 출석 처리 대상인지 확인한다. 우선 애플리케이션에서 검증하고, 3차에서 DB 제약조건을 통한 보강 방법을 검토한다.
- **조회·분석:** JOIN으로 회원별 참여 스터디와 모임 정보를 조회하고, GROUP BY·COUNT 등을 통해 인원·출석·활동 현황을 집계한다. 검색·필터·서브쿼리 및 인덱스도 실제 사용 사례에 맞춰 구현한다.

### 6-3. 접근 권한 및 이력 관리 계획

- **공지사항 및 활동 기록 접근:** 현재 스터디 구성원에게만 공지사항과 활동 기록 열람을 허용한다. 공지사항은 스터디장이 관리하고, 구성원은 활동 게시글과 댓글을 작성할 수 있도록 한다. 접근 권한은 화면뿐 아니라 서버에서도 검증한다.
- **신청과 재가입의 구분:** 취소·거절된 신청 이후의 **재신청은 허용**하고 기존 신청 행을 보존한다. 실제 구성원으로 가입했다가 탈퇴한 이후의 **재가입 처리**(새 소속 행 생성 또는 기존 행 재활성화)는 아직 확정하지 않는다.
- **과거 활동 기록:** 탈퇴자의 게시글·출석 기록 보존 방식과 탈퇴 후 접근 권한은 개인정보 보호와 운영 이력 관리 필요성을 고려하여 2차에 결정한다.

### 6-4. 이후 단계에서 구체화할 세부사항

스터디 종료·삭제 정책, 회원 탈퇴에 따른 기록 처리, 탈퇴 회원의 재가입, 출석 상태의 세부 종류, 공지·게시글 수정 권한, 인증 방식, 자료형 및 정규화 범위 등은 2~3차에서 구체화한다. 해당 사항은 요구사항을 구체화하고 구현 가능성을 검토한 후 결정한다.

## 7. 향후 구현 계획

| 단계 | 목표 | 주요 산출물 |
| --- | --- | --- |
| **1차: 프로젝트 기획** | 문제·사용자·핵심 기능·운영 정책·테이블 후보 제시 | 본 기획안 `proposal.md`, 발표용 설명 자료 |
| **2차: 요구사항 고도화** | 1차 피드백 반영, 화면 구조·업무 흐름 구체화, ERD 초안 제작 | 요구사항, 화면 및 기능 흐름, ERD 초안, 변경 이력 |
| **3차: DB 분석 및 설계** | 테이블·자료형·PK/FK·정규화·제약조건 확정, 주요 SQL 및 트랜잭션 설계 | 최종 ERD, 테이블 명세서, SQL 스크립트, 테스트 데이터 |
| **4차: 실제 구현** | PostgreSQL 연동 웹 애플리케이션 구현, 주요 기능 시연·검증 | 실행 가능한 서비스, 시연 자료, SQL 활용·문제 해결 보고 |

### 7-1. 단계별 구현 범위

- **필수 구현 흐름:** 회원·스터디 관리 → 참여 신청·승인과 정원 검증 → 구성원·일정·출석 관리 → 공지·활동 기록·태그 검색 → 간단한 SQL 통계. 단계별로 작동 여부를 검증한다.
- **구현 범위 관리:** 12개 테이블을 중심으로 개발하되 채팅, 실시간 알림, 결제, 파일 업로드 등 부가 기능은 구현 대상에서 제외한다. 통계는 별도의 통계 저장 테이블 없이 기존 데이터를 SQL로 집계한다.
- **설계 발전:** 2차에는 화면·권한·업무 흐름과 ERD 초안을 확정하고, 3차에는 스키마·샘플 데이터·주요 SQL과 트랜잭션을 검증한 뒤, 4차에는 검증된 DB를 웹서비스에 연동한다.

### 7-2. 개발 환경

- **데이터베이스:** PostgreSQL
- **DB 관리·검증:** DBeaver
- **개발 및 문서:** VS Code, Markdown
- **버전 관리 및 제출:** GitHub
- **웹 애플리케이션 기술:** 2차 요구사항 및 화면 설계 결과를 바탕으로 구현 난이도와 PostgreSQL 연동 편의성을 비교하여 선정

본 프로젝트에서는 **테이블의 필요성과 관계 설정 근거, 데이터 무결성, SQL 활용 사례**를 설계와 구현 결과로 제시하고자 한다. 이를 위해 1차 기획을 출발점으로 요구사항 분석, 데이터베이스 설계, 애플리케이션 구현을 단계적으로 진행한다.
